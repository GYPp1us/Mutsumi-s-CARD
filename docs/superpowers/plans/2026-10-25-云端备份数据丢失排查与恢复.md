# 云端增量备份数据丢失：排查与恢复方案

## 当前结论与边界

以当前主分支 / v0.9.0 的代码为依据，已确认增量备份存在实际删除本地数据的路径，且远端发布失败不代表本地未变更。

用户更正连接信息后，只读认证已通过，已保全九份快照和 43 张 PNG，其中十张未被任何快照引用的卡面经用户确认正是本次丢失内容。已生成十张卡片的本地恢复 ZIP，并通过原应用格式验证及新副本导入流程校验。原始 PNG 完整；文字 key 根据卡面临时重建，原卡组关系、创建时间和复习记录无法从这批 PNG 中恢复。尚未在用户设备实际导入，也未修改云端内容、应用生产逻辑或发布 APK。

密码只经不回显输入进入进程内存，未写入脚本、仓库或命令行参数；认证会话已结束。真实证据位于忽略目录 `artifacts/cloud-recovery-20261025-r2`，交付文件另存主工作区的 `artifacts/recovery-20261025`，真实原件、内容映射和恢复包均不进入 Git 提交。

## 已确认的实现问题

1. `CloudBackupService.kt` 的 `backup()` 先读取本地快照，再下载云端快照、执行合并；结果有差异便以 `deleteExtras = true` 调用 `applyCloudSnapshot()`。
2. `CloudConflictResolver.mergeRecords()` 把“基线有记录、本地没变、云端没有记录”解释为云端删除，即使本轮没有打开推送删除，也可能删除本地记录。一个较新的备份索引并不能证明其中缺少的记录确实被用户删除。
3. `RoomCloudBackupDataAccess` 会按合并结果删除数据库记录，并把其图片路径加入持久删除队列。这不是列表隐藏或只刷新界面。
4. 备份开始后仍可通过其他页面写入卡片。读取本地快照与最终精确覆盖之间没有事务版本校验，新写入但未纳入旧快照的卡片可能被当作“额外项”删除。
5. 本地覆盖发生在远端索引 `putIfUnchanged()` 之前。索引竞争失败会报错，但不会撤销已经发生的本地覆盖；旧测试只核对索引和基线，没有验证本地数据仍完整。
6. `restore()` 同样在最终应用时强制开启本地删除；关闭拉取删除不保证安全。因此恢复本次事故时不使用现版云端恢复按钮。
7. 应用启动选择卡组前会执行 `retryPendingImageCleanup()`，删除队列中的图片可能在下次启动时被清除。

### 时间戳的准确含义

当前代码按 `index.snapshots.first()` 选取索引中的当前版本，不以 `createdAt` 最大值裁决单条卡片。仅仅让云端备份时间晚于本地新增时间，并不足以删除一个不在本机基线中的、且在本轮读取本地快照之前就存在的新卡片。

因此已验证的删除缺陷不能直接等同于本次用户观察的唯一原因。还需核对真实快照、设备基线、删除开关和操作时序。

## 四个复现场景

`CloudBackupDataLossReproductionTest.kt` 是对原有危险行为的特征测试，断言删除发生用于确认缺陷；测试通过不是修复完成。

| 场景 | 原版本结果 |
| --- | --- |
| 本地新增尚未上传，其他设备仅生成更晚的普通备份 | 本地新增保留，证伪“时间较晚本身就会删除” |
| 旧设备推送删除使云端缺少基线记录，另一设备普通备份 | 另一设备的对应卡片被静默删除 |
| 云端独立修改需要回写，网络读取期间本地新增卡片 | 新增卡片被精确覆盖删除 |
| 上述本地覆盖后，远端索引竞争失败 | 备份报错、基线不推进，但本地卡片已删除 |

## 真实云端取证结果

- 发现并保存九份快照：八份在索引中，另有一份较早快照不在索引中。
- 北京时间 2026-10-24 20:46:15、20:39:50 和 2026-09-06 15:19:49 的三个快照 JSON 字节完全相同，均为 31 张卡。新备份的时间不能证明它包含更新的内容。
- 保存全部 43 张 PNG，共 8,045,586 字节；全部通过对象名 SHA-256 校验和 Pillow 完整解码。图片保全前后索引一致。
- 其中十张 PNG 不被任何已发现快照引用，均为 1024×1624。目录报告的修改时间在北京时间 2026-10-24 20:46:09 至 20:46:15，与事故备份相邻。用户检查主题后确认它们正是丢失卡面。
- 当前备份实现上传 `current.bytesByHash` 中的原始图片，却把合并后的 `effective` 写入快照。上述“新图片留存、旧快照不变”证据与该危险路径吻合；但尚无原设备版本、基线和完整时序，不能仅凭云端断言唯一触发条件。
- 原始审计中另有十条“历史稳定 ID 缺失”候选：其中八条的 key 和图片内容已在当前版本存在，涉及旧数字 ID 到稳定 ID 的变化；另外两条来自七月早期记录，不能与本次十张孤立 PNG 混同。独立复核结果保存在私有交付目录，不改写原始审计。

## 恢复顺序

### 一、停止扩大损失并保全原件

- 暂停所有设备向同一目录进行云备份、云恢复或删除操作，避免八版本保留窗口继续滚动。
- 不卸载、不清空数据。不以旧 ZIP 覆盖原数据库；若问题设备已经退出，先不要再次启动触发待删除图片清理。
- 如果仍有完整数据的设备，先保全其数据与本地 ZIP。问题设备的原始数据库、WAL/SHM、`cloud-sync-baseline.json`、`card-store-v2` 图片与删除队列需要在可合法访问应用私有目录的条件下复制保存；不假设正式应用允许普通 ADB 直接读取私有目录。

### 二、云端只读取证

确认用户提供的实际域名后，仅使用 GET 和 PROPFIND：

1. 保存原始 `index.json` 和各文件目录信息。
2. 保存保留窗口内的快照，并枚举 `snapshots/` 中未被当前索引引用的 JSON。发布失败可能留下这类快照，不能只看页面上的八个版本。
3. 对比每个版本的稳定卡片 ID、key、卡组和正反面图片哈希，生成当前版本缺失记录与历史内容变体清单。历史缺失记录也可能是用户有意删除，不能全部自动认定为误删。
4. 保存相关 PNG 并验证 SHA-256；同时列举 `objects/` 中没有快照引用的图片。这类对象可能保留卡面，但未必有原 key、卡组或复习状态。
5. 再读一次索引，标记取证期间是否发生其他设备写入。原始材料另存，不回写用户目录。

### 三、生成恢复副本并验证

- 有完整元数据和 PNG 的历史版本，可转换为原应用格式的本地 ZIP。卡组加“恢复副本”及版本 ID，保留原数据、双面图、时间与复习状态，使用独立本地图片路径。
- 先核验 ZIP 清单、SHA-256、图片尺寸与资源引用，再通过“本地备份 → 从文件恢复”导入新副本。该路径走 `BackupImporter.importCopy()`，与存在精确覆盖风险的云端恢复不同。
- 导入前再次保全现状；导入后核对卡片数量、key、正反面和复习状态，再决定是否人工合并重复项。恢复材料始终保留。
- 超过原应用 64 MiB 导入限制的快照需要分批处理；工具会拒绝生成超限包，不把超限包当作可导入成果。

### 可恢复程度的限制

- 历史快照与其 PNG 完整：可恢复对应卡组、卡片和复习状态。
- 仅保留图片：只能尝试恢复卡面并人工补 key、分组，不能伪造原复习状态。
- 从未上传的新增记录：云端不一定存在其元数据，需查原设备、其他设备或已有本地备份。
- 历史快照和对象已清理、原机数据也不在：不能承诺完整恢复；需要进一步检查存储服务本身的历史版本或设备备份。

## 只读工具

`scripts/cloud_backup_recovery.py` 的网络方法仅允许 GET / PROPFIND，禁止自动跟随重定向携带凭据；密码从交互式输入或专用进程环境变量读取，不作为 CLI 参数、文件内容或报告字段保存。

示例（只含占位信息）：

```powershell
# 先列出已确认 DAV 根目录，找到应用配置使用的实际目录。
python scripts/cloud_backup_recovery.py --url https://example.test/dav/root --username USER --output artifacts/recovery-discover --discover

# 保存全部可发现快照与目录信息，暂不下载图片。
python scripts/cloud_backup_recovery.py --url https://example.test/dav/root --username USER --remote-directory MutsumiCard --output artifacts/recovery-audit

# 将指定版本的原件、图片和恢复 ZIP 保存在一个全新目录。
python scripts/cloud_backup_recovery.py --url https://example.test/dav/root --username USER --remote-directory MutsumiCard --output artifacts/recovery-selected --restore-snapshot 1234567890000-UUID
```

`--download-images` 可保全所有发现版本引用的图片，`--include-orphans` 可额外保存未引用 PNG。已有取证目录和恢复 ZIP 不会被覆盖。脚本无修改远端索引、上传或删除远端文件的实现。

## 应用修复应满足的门禁

恢复优先于把有争议的合并结果写回设备。后续修复至少覆盖：

1. 普通备份不能静默删除本地记录；远端“缺席”不再直接充当已确认删除。
2. 删除策略要区分方向、共同基线和明确删除意图；缺失或过期基线应保守保留数据。
3. 本地快照与提交之间的并发写入应在 Room 事务内做版本校验，不能只在网络请求之前加互斥锁。
4. 任何会改变本地数据的云操作前，应留下可独立恢复的持久安全副本。
5. 远端发布失败、本地事务失败、应用中断均必须保持可恢复状态；同时验证数据库、图片、基线与远端索引。
6. 将四个特征测试中的危险行为改成“拒绝操作或保留数据”的回归断言，再完成设备与正式包验收。当前复现测试不能作为修复版发布门禁。
